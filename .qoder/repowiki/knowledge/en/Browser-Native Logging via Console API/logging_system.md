The repository employs a **browser-native logging strategy** relying exclusively on the standard `console` API (`console.log`, `console.warn`, `console.error`). There is no dedicated logging framework, middleware, or centralized logging service.

### 1. Logging Approach
- **Framework**: None. The application uses built-in browser console methods.
- **Levels Used**:
  - `console.log`: General status updates, configuration confirmations, and cache hits (e.g., "ONNX Runtime configured", "Model loaded from cache").
  - `console.warn`: Non-critical failures, fallbacks, or deprecated feature usage (e.g., "Cache read failed", "Codec not supported").
  - `console.error`: Critical errors that halt execution or indicate significant failures (e.g., "ONNX Runtime not found", "Folder selection error").
- **Structure**: Logs are primarily unstructured strings, often concatenated with variables. Some modules use simple prefixes like `[缓存]` (Cache) or `[profiling]` to categorize output in the developer console.

### 2. Key Files
- `js/ai_upscale.js`: Contains extensive logging for model loading, caching (IndexedDB/Cache API), and ONNX Runtime configuration.
- `js/ai_frame_interpolation.js`: Uses logging for ORT runtime preloading, preview synchronization, and model loading states.
- `js/3d_city.js`: Logs warnings for Cesium terrain and map layer loading failures.
- `third_part/ort-wasm-simd-threaded.js` (and other ORT bundles): Contains internal profiling logs (e.g., `[profiling] kernel ... execution time`) generated by the ONNX Runtime WebAssembly backend when profiling is enabled.

### 3. Architecture & Conventions
- **Decentralized**: Each JavaScript module handles its own logging inline. There is no shared logger instance.
- **Error Handling Pattern**: `try/catch` blocks are widely used. Errors are typically logged to the console and then either re-thrown, returned as a rejected promise, or handled by updating the UI status (e.g., `setModelStatus`).
- **Profiling**: Performance logging is embedded within the ONNX Runtime integration, outputting kernel execution times directly to the console when specific environment flags are set.

### 4. Developer Rules
- **Use Standard Console**: Continue using `console.log/warn/error` for debugging and status reporting.
- **Contextual Prefixes**: When adding new logs, consider using square-bracket prefixes (e.g., `[Module]`) to make filtering in the browser DevTools easier.
- **No Persistent Logs**: The system does not currently support persistent log storage (e.g., sending logs to a server or saving to a file). All logs are ephemeral and visible only in the browser's developer console.
