Two complementary delivery patterns coexist:
- **Static single-page tools** (e.g. `3d_city.html`, `TA_wiki.html`): each HTML file is self-contained, loads shared `menu.js` + `waifu.js` plus its own CSS/JS, and owns its DOM directly.
- **Workbench-injected tools** (e.g. `chatgpt.html`, `video_cut.html`, `ai_draw.html`): the HTML contains only an empty `<div id="panel" data-local-tool="...">`; `js/local_workbench.js` reads that attribute at `DOMContentLoaded`, builds a `.tool-shell` host, then dispatches to per-tool init functions (`initChatTool`, `initVideoCut`, `initAiDrawTool`) which in turn call the tool module's exported `window.initXxxTool` if available, otherwise fall back to inline stubs or redirect to `designtool.site` via `designToolLinks`.
- Shared infrastructure lives outside the scope: `js/menu.js` injects the left navigation into every page, `css/common.css` defines the sidebar/top-search/main-panel layout, and `css/local_workbench.css` styles the injected workbench shell.
- Tool modules are independent JS files under `js/` with no cross-imports; they communicate with the host only through `window.initXxxTool` callbacks or by reading/writing elements inside their assigned `#panel` subtree.
- External libraries are loaded from CDN per-tool (Cesium, Leaflet, model-viewer, marked, DOMPurify, Fuse.js) rather than centralized, keeping each HTML entry point fully portable.
